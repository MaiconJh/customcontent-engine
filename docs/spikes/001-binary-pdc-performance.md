# Spike 1 - Binary PDC Performance

Status: Completed  
Date: 2026-06-06  
Scope reference: `docs/PROJECT_SCOPE.md` Spike 1 - Binary PDC Performance

## 1. Objective

Measure the in-memory cost of the current binary PDC codec used to persist custom block identities.

The measured format is unchanged:

```text
Byte 0: schema version
Bytes 1-2: entry count, big-endian
Each entry:
  - packed position as short
  - numeric_id as short
```

This spike measures the current `PdcBlockCodec` behavior only. It does not change persistence, gameplay, PDC storage, cache policy, or MVP scope.

## 2. Scope

Measured entry counts:

- 256 entries.
- 512 entries.
- 1024 entries.

Measured operations:

- `encode`.
- `decode`.
- `lookup/findNumericId`.
- `add/upsert`, implemented in the spike as decode, add missing entry, encode.
- `remove`.

Out of scope for this spike:

- Bukkit `PersistentDataContainer` read/write overhead.
- Chunk NBT serialization cost.
- Full Paper event cost under player load.
- Cache design.
- Persistence format changes.
- Mechanics or MVP-1 behavior.

## 3. Test Environment

- OS: Windows 10 10.0 amd64.
- Java: 21.0.11.
- Gradle task: `./gradlew binaryPdcSpike --no-daemon`.
- Warmup iterations per operation: 2,000.
- Measured iterations per operation: 8,000.
- Allocation measurement: approximate per-thread allocated bytes via `com.sun.management.ThreadMXBean`.

The spike is intentionally lightweight and deterministic. It is not a JMH benchmark and should be interpreted as directional data for MVP planning.

## 4. Methodology

The spike creates synthetic codec entries using the same packed-position helper currently used by `PdcBlockCodec`.

For each entry count:

1. Build a list of `PdcBlockEntry` values.
2. Encode the list into the current byte-array format.
3. Warm up each operation.
4. Measure average wall-clock time per operation with `System.nanoTime()`.
5. Measure approximate thread-local allocation per operation when available.

The `lookup/findNumericId` and `remove` scenarios target an existing entry near the end of the encoded list, exercising the current linear scan behavior.

The `add/upsert` scenario decodes the existing payload, adds a missing entry, and encodes the updated list, matching the current adapter-level full read/modify/write model.

## 5. Scenarios Measured

| Entries | Payload size |
| ---: | ---: |
| 256 | 1,027 bytes |
| 512 | 2,051 bytes |
| 1024 | 4,099 bytes |

Payload size is calculated from the current format:

```text
3 byte header + entry_count * 4 bytes
```

## 7. Interpretation

The binary payload remains compact at all measured sizes. At 1024 entries, the encoded payload is approximately 4 KB.

The measured operations are linear where expected:

- `decode` allocates one entry record per decoded block.
- `lookup/findNumericId` decodes then scans entries.
- `add/upsert` decodes, copies to a mutable list, updates/adds, and encodes.
- `remove` decodes, filters, and encodes.

The worst measured average operation at 1024 entries was `lookup/findNumericId` at about 62 microseconds/op in this environment. `remove` and `add/upsert` were in the same general range.

For MVP-1 planning, the current format appears acceptable as a simple canonical storage format, provided area operations remain budgeted and do not perform unbounded many-block work in a single tick.

## 8. Risks Found

- Lookup/remove currently decode the whole payload and allocate entry objects.
- Allocation is linear with entry count.
- The spike does not include Bukkit/Paper PDC access overhead.
- The spike does not simulate 50 concurrent players or repeated area mechanics.
- The current packed position format supports Y values from 0 to 255 only; this was already known from codec tests and was not changed by this spike.

## 9. Recommended Decision

Recommendation: keep the current binary format for MVP-1 planning.

Reasoning:

- Payload size is compact.
- Measured in-memory codec costs are small enough for MVP-scale operations.
- The format matches the approved persistence rules.
- No benchmark result justifies changing persistence before MVP-1 planning.

No ADR is required for this recommendation because no persistence format, scope, scheduler, Folia, or mechanic contract change is being made.

If future Paper event/load tests show unacceptable tick impact, a format or indexing change should be proposed through an ADR instead of being implemented directly.

## 10. Next Steps

- Keep `PdcBlockCodec` format unchanged.
- Use `WorkBudget` and bounded operation counts when planning MVP-1 mechanics.
- Treat any future cache or persistence format change as ADR-required.
- Run additional Paper-level load tests before expanding area operations beyond MVP-1's approved limits.
- Proceed to Spike 2 - Folia cross-region behavior before implementing advanced Folia-sensitive behavior.
